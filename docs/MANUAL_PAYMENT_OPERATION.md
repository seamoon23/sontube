# SonTube 계좌이체 결제 운영 가이드

## 범위

SonTube 초기 유료 운영은 PG나 자동결제 없이 `선불 이용권 선택 → 사업용 계좌 입금 → 최종관리자 수동 확인 → 가족 이용권 생성·연장` 순서로 동작한다.

- 부모 경로: `보호자 관리자 > 이용권·결제` (`/admin/payment`)
- 최종관리자 로그인: `/superadmin/login`
- 입금 처리: `최종관리자 > 결제` (`/superadmin/payments`)
- 결제·환불 대사 CSV: `최종관리자 > 결제 > 전체 CSV 내려받기`
- 상품 설정: `최종관리자 > 요금제` (`/superadmin/plans`)
- 가족·보호자 계정: `최종관리자 > 사용자` (`/superadmin/users`)
- 처리 이력: `최종관리자 > 감사 로그` (`/superadmin/audit`)

카드결제, 자동이체 조회, 오픈뱅킹, 가상계좌, 자동갱신과 인앱결제는 연결하지 않는다.

## 환경변수

실제 값은 저장소가 아니라 운영 서버의 비밀 환경변수에 넣는다. `.env.example`은 이름만 제공한다.

### 보호자 bootstrap

- `SESSION_SECRET`
- `ADMIN_ALLOWED_EMAILS` (서로 다른 운영 보호자 이메일 정확히 두 개)
- `ADMIN_PASSWORD_HASH`
- `PARENT_BOOTSTRAP_EMAIL`
- `PARENT_BOOTSTRAP_FAMILY_NAME`

### 최종관리자

- `SUPERADMIN_LOGIN_ID`
- `SUPERADMIN_PASSWORD_HASH`
- `SUPERADMIN_SESSION_SECRET`

최종관리자 비밀번호와 세션 비밀키는 보호자용 값과 반드시 다르게 만든다.

### 사업자·계좌 안내

- `PAYMENT_BUSINESS_NAME`
- `PAYMENT_BUSINESS_NUMBER`
- `PAYMENT_BANK_NAME`
- `PAYMENT_ACCOUNT_NUMBER`
- `PAYMENT_ACCOUNT_HOLDER`
- `PAYMENT_CONFIRMATION_NOTICE`
- `PAYMENT_SUPPORT_CONTACT`
- `PAYMENT_REFUND_POLICY`

필수 사업자·계좌·문의 항목이 비어 있으면 부모의 입금 신청 버튼이 비활성화된다. 계좌번호는 서버 렌더링된 결제 안내 화면에만 표시하며 일반 로그나 감사 로그에 기록하지 않는다.

## 최초 설정 경로

시작 위치는 `C:\codex\app\sontube`의 PowerShell이다.

1. 보호자 비밀번호 해시를 만든다.

```powershell
npm run auth:hash -- <보호자비밀번호> <SESSION_SECRET>
```

2. 별도 비밀키로 최종관리자 비밀번호 해시를 만든다.

```powershell
npm run auth:hash -- <최종관리자비밀번호> <SUPERADMIN_SESSION_SECRET>
```

3. `.env`에 위 환경변수를 넣고 `ADMIN_ALLOWED_EMAILS`의 두 이메일 중 하나를 `PARENT_BOOTSTRAP_EMAIL`로 지정한다. 이 파일은 커밋하지 않는다.
4. DB를 준비하고 bootstrap 가족과 비활성 기본 상품을 만든다.

```powershell
npx prisma migrate deploy
npm run db:seed
```

5. 브라우저에서 `/superadmin/login`으로 들어가 `최종관리자 > 요금제`에서 가격을 입력하고 상품을 활성화한다. 시드 상품은 사고 방지를 위해 처음에는 `0원/비활성`이다.
6. `/admin/login`에서 bootstrap 보호자 이메일로 로그인해 `보호자 관리자 > 이용권·결제` 안내를 확인한다.

기존 마이그레이션 이력이 없는 DB를 업그레이드할 때는 앱 쓰기를 중지하고 `npm run ops:backup`과 `npm run ops:backup:verify`로 DB·`public/uploads/thumbnails`를 같은 시점에 백업한 뒤 스테이징에서 먼저 복구한다. 환경변수는 archive에 포함되지 않으므로 호스팅 secrets에서 별도로 암호화 보관한다. 상세 명령과 복구 순서는 `docs/OPERATIONS_RUNBOOK.md`를 따른다. 기존 스키마가 이미 있는 DB는 baseline만 적용된 것으로 기록한 뒤 업그레이드를 실행한다.

```powershell
npx prisma migrate resolve --applied 20260702000000_baseline
npx prisma migrate deploy
npm run db:seed
```

빈 DB에서는 `npx prisma migrate deploy`가 baseline, 가족·결제, 채널, Lite 공개와 보호자 세션 버전 migration을 순서대로 모두 적용한다. 현재 순서는 아래와 같고, 빈 임시 SQLite DB에 실제 적용한 뒤 현재 `schema.prisma`와 차이가 없음을 검증한다.

1. `20260702000000_baseline`
2. `20260730090000_add_family_manual_payment`
3. `20260730120000_add_video_channels`
4. `20260830090000_add_lite_catalog`
5. `20260830120000_add_parent_user_session_version`

## 상품과 신청 규칙

- 기본 상품은 90일과 365일 두 개이며 가격과 활성 상태는 최종관리자가 DB에서 설정한다.
- 부모가 보낸 금액은 신뢰하지 않는다. 신청 시 서버가 활성 상품의 현재 가격과 기간을 스냅샷으로 저장한다.
- 같은 가족·같은 상품의 `PENDING` 신청은 하나만 유지하며 기존 신청번호를 반환한다.
- 신청만으로 앱 이용권은 활성화되지 않는다.
- 입금증 이미지는 받지 않는다.
- 입금자명, 입금일, 신청번호, 신청 금액과 보호자 계정을 기준으로 수동 대조한다.

## 승인 처리

`최종관리자 > 결제 > 신청 상세`에서 은행 입금내역을 먼저 확인한다.

1. 실제 입금액과 입금일을 입력한다.
2. 예정 금액과 실제 입금액이 정확히 일치하는지 확인한다.
3. `입금 확인 및 이용권 활성화`를 누른다.
4. 결제 상태 변경, 이용권 생성·연장, 앱 키 `paidUntil` 반영, 감사 로그를 한 DB 트랜잭션으로 처리한다.

현재 활성 이용권이 있으면 기존 만료일에서 상품 일수만큼 연장한다. 없거나 만료됐으면 승인 시각부터 시작한다. `paymentRequestId`별 지급 레코드가 하나뿐이므로 같은 승인을 반복해도 기간이 두 번 늘어나지 않는다.

처리 불가 건은 `확인 불가`, 오래된 미입금 건은 `신청 만료`로 바꾼다. 처리 완료 신청을 되살리지 않고 부모가 새 신청을 만들게 한다.

## 환불 처리

현재 MVP는 전액 환불만 지원한다.

1. 부모가 결제 내역에서 전액 환불을 요청한다.
2. 최종관리자가 정책과 실제 이용 상황을 검토한다.
3. 승인할 경우 먼저 실제 계좌 송금을 완료한다.
4. 그 다음 시스템에서 `환불 완료`를 기록한다.

환불 완료는 가장 최근의 활성 이용권 지급 건에만 자동 적용한다. 그 뒤에 다른 연장 결제가 있으면 자동 회수를 막고 운영자가 결제 순서부터 확인해야 한다. 환불 반려 시 결제는 다시 `입금 확인 완료` 상태가 된다.

부분 환불, 이용 기간 비례 산식과 계좌이체 수수료 정책은 아직 구현하지 않았다. 공개 판매 전에 정책 문구를 법률·세무 기준에 맞게 확정한다.

## 현금영수증

현재 결제 폼은 휴대전화번호나 사업자번호 같은 현금영수증 식별정보를 저장하지 않는다. 부모는 신청번호와 함께 고객지원으로 요청한다. 자동 저장을 추가하려면 별도 테이블, 암호화 키, 마스킹, 보존 기간과 접근 로그를 먼저 설계해야 한다.

## 최종관리자와 대체 로그인

최종관리자는 DB 사용자 권한이 아니라 운영 환경변수에만 존재한다. 보호자 계정이 최종관리자로 승격되는 경로는 없다.

- 최종관리자 세션: 4시간
- 대체 로그인: 최종관리자 비밀번호 재확인과 5자 이상의 사유 필수, 30분
- 대체 로그인 중: 지속 배너 표시
- 차단 작업: 영상·Lite 공개·태그·채널·앱 키·통신 정책·결제를 포함한 모든 데이터 변경
- 시작·종료: `SuperAdminAuditLog`에 기록

보호자 세션에는 DB의 `sessionVersion`을 서명해 넣는다. 비밀번호 재설정, 보호자 활성 상태 또는 가족 활성 상태 변경 시 버전을 증가시켜 기존 세션을 즉시 폐기한다.

대체 로그인은 화면과 재현 절차 확인용이다. 부모가 입력한 비밀번호나 앱 키 원문은 볼 수 없다.

## 매일 운영

1. `최종관리자 > 결제`에서 입금 대기와 환불 요청을 확인한다.
2. 사업용 계좌 내역과 신청번호·입금자명·금액·입금일을 대조한다.
3. 일치 건만 승인하고 불일치는 내부 관리자 메모를 남긴다.
4. 부모 화면에 상태가 반영됐는지 확인한다.
5. `최종관리자 > 감사 로그`에서 승인, 환불, 대체로그인 이력을 확인한다.

월별로 `최종관리자 > 결제 > 전체 CSV 내려받기`에서 결제·환불 대사 파일을 받아 실제 계좌 내역과 맞춘다. CSV는 신청·입금·환불 금액과 처리 시각을 포함하고 자유 메모와 내부 ID는 제외한다. DB·썸네일·환경변수 백업 복구 테스트도 함께 수행한다. SQLite는 단일 인스턴스와 영속 디스크가 필요하다. 다중 서버 또는 서버리스 운영 전에는 관리형 DB와 영속 rate limit로 이전한다.

## 보안과 법률 주의

- 비밀번호, 앱 키 원문, 계좌 비밀번호, 사용자 전체 계좌번호와 입금증 전체 화면을 수집하지 않는다.
- 계좌번호와 예금주는 소스, 클라이언트 환경변수, 일반 로그와 감사 metadata에 넣지 않는다.
- 승인·환불 로그는 운영 UI에서 삭제 기능을 제공하지 않는다.
- 공개 유료 판매 전 사업자등록, 통신판매업 신고 여부, 환불정책, 현금영수증과 세무 처리를 실제 조건에 맞춰 확인한다.
- 이 문서는 개발·운영 가이드이며 법률 또는 세무 자문을 대체하지 않는다.

## PG 전환 기준

월 입금 처리량, 환불·미입금 문의, 확인 지연 또는 정기결제 요구가 커지면 PG나 가상계좌를 검토한다. 상품, 결제 신청, 가족 이용권, 지급 건, 환불과 감사 로그가 분리되어 있어 결제 수단을 바꿔도 이용권 핵심 모델은 유지할 수 있다.
